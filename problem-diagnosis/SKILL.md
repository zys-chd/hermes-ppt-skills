# 问题诊断与排查框架

用户描述了问题现象但**还没有分析结果**时，帮他拆问题、选对方法、列出可执行的排查清单。

**核心价值**：不给答案，给**排查路径** —— 哪些假设要验证、怎么验证、什么结果算排除。

## 什么时候用
- "客户投诉 XX，我该从哪查起？" / "设备老故障，帮我理清思路" / "给我个排查清单"
- 任何"有现象、无结论、需要方法论"的场合

**不用**：已有数据要分析 → 直接分析；纯粹要排版 → ppt-builder。

---

## 工作流程（四步）

### 1. 问清边界（不要跳过）
缺的才问，一次 3~5 个：现象是什么 / 范围对象 / 时间特征 / **已排除什么** / 可用证据 / 影响紧迫度。
用户说"不清楚"的，按最保守假设推进并标注假设。

### 2. 选方法（1 主 + 1~2 辅，最多 3 个）
按问题类型查下表，**必须说明为什么选这几个**。

| 问题类型 | 主方法 | 辅助 |
|---------|--------|------|
| 偶发突发故障、原因不明 | 5Why + 鱼骨图 | 4M1E |
| 同类问题反复出现 | 8D | 帕累托 + 5Why |
| 质量问题、批量失效 | 4M1E | 鱼骨图 + 分层交叉 |
| 复杂系统、多条失效路径 | **FTA 故障树** | FMEA |
| 风险预防（还没出事） | FMEA | 鱼骨图 |
| 问题多、先抓主要矛盾 | 帕累托 | 分层分析 |
| 数据异常、指标突变 | 分层 + 交叉分析 | SPC 控制图 |
| 判断"真异常还是正常波动" | **SPC 控制图** | 分层 |
| 有数据、验证因素是否真有效 | **DOE / 假设检验** | SPC |
| 流程/管理类问题 | 5W2H + 5Why | 流程图 |
| 向上汇报问题解决过程 | **A3 报告** | 8D |
| 多方案/多假设需结构化比较 | **KT 法** | 帕累托 |
| 完全没头绪 | 5W2H + 鱼骨图 | — |

> 每个方法的具体做法见 `references/methods.md`（按需查阅，不要凭印象写）。
> 完整示例见 `references/example-injection-molding.md`（4M1E 场景）和
> `references/example-servo-fault-tree.md`（FTA 场景，含质量标杆说明）。

### 3. 拆解问题空间
每个分支都要落到**可观察、可验证**的具体项。写"设备异常"不算，要写"主轴径向跳动是否超 0.02mm"。

### 4. 产出 checklist（核心交付物）

六列，每条可直接执行：

```markdown
| # | 排查项 | 怎么查（具体动作） | 判据（★排除性 / ☆倾向性） | 证据 | 负责人 | 状态 |
|---|--------|------------------|--------------------------|------|--------|------|
| 1 | 批次A是否问题批次 | 调BOM+来料检验记录，比对问题机号段 | ★号段不重合→排除该假设 | 来料记录、机台日志 | 待定 | ☐ |
| 2 | 是否某子集集中 | 按批次/产线/时间分层统计 | ☆某子集占比>60%→嫌疑锁定，需[5]确认 | 分层统计表 | 待定 | ☐ |
| 3 | 低温下是否复现 | 温箱 DOE，前后各 200 件 | ★复现→锁定料×环交互；不复现→排除环境 | DOE 报告 | 待定 | ☐ |
```

**必须有的三点**：

- **怎么查**要具体（"调取 BOM 和来料记录比对号段"，不是"检查物料"）
- **判据分级**（关键，避免把弱证据当结论）：
  - `★ 排除性`：一刀切，结果明确可排除或锁定某个假设（如"号段不重合→排除"）
  - `☆ 倾向性`：结果只是提高嫌疑，还需进一步验证（如"占比>60%→嫌疑，需后续确认"）
  - 混用这两种是常见错误 —— 把"☆倾向"当"★排除"会过早收敛到错误方向
- **依赖关系**写进判据或怎么查里：`需先完成[2]再做` / `依赖[1]的结果`
  （如"做 DOE 前必须先确认批次分布，否则分不清是料还是环"）

**排序**：按**排除效率**排，优先放能一刀切掉大范围假设的项（不是按方法顺序）。
可执行顺序 = 依赖关系拓扑 + 排除效率，两者冲突时以依赖为先。

## 输出结构

```
## 问题界定          —— 5W2H 说清现象/范围/时间/影响/已排除
## 分析方法选择      —— 主方法 + 辅助方法（附理由）
## 排查框架          —— 用选定方法结构化拆解（文字版即可）
## 排查清单（核心）   —— 六列表格，按排除效率排序
## 验证优先级        —— 第一批砍范围 / 第二批确认根因 / 第三批验证对策
## 需要补充的信息     —— 还缺什么才能进一步收敛
```

## 常见错误

- ✗ 堆 8 个方法 → 用户淹没。1 主 + 1~2 辅。
- ✗ checklist 写成"检查设备" → 不可执行。
- ✗ 没有判据 → 查完不知道算不算查到。
- ✗ 直接给根因结论 → 没数据时猜根因是幻觉，给假设和验证路径。
- ✗ 忽略"已排除什么" → 重复用户做过的事。
- ✗ 按方法顺序排序 → 应从最省力、最能砍范围的查起。

## 引用数据必须标来源

涉及行业经验值、基准数据、标准限值时（如"行业常见故障率 0.5~1%/年"），
**必须**标注来源或明确标为经验估计。写法：
- ✓ "据 IEC 61508 的 SIL 分级要求……"（有出处）
- ✓ "经验估计（未经核实）……"（明确不确定）
- ✗ "行业常见 0.5~1%/年"（无来源、无标注，像事实陈述）

不确定就说不确定。编造具体数字比不给数字危害更大 —— 用户可能据此做决策。

## 衔接 PPT
排查完要出汇报时，把产出交给 `ppt-builder`。排查清单可直接变成 PPT 的"排查矩阵页"，
排除项保留展示能体现严谨性。
