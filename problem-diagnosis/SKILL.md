# 问题诊断与排查框架

**触发场景**：用户描述了一个问题现象（可能只有几句话），但**还没有分析结果**，
希望有人帮他把问题拆开、选对方法、列出要逐一排查的清单。

**核心价值**：不是给答案，而是**给出靠谱的排查路径**——哪些假设要验证、怎么验证、
什么结果算排除、什么结果算嫌疑最大。让用户拿着清单能直接开干。

## 什么时候用
- "客户投诉 XX 问题，我该从哪查起？"
- "设备老是故障，帮我理清排查思路"
- "给我一个排查清单"
- "问题背景是 XX，帮我用几个分析工具拆一下"
- 任何"有现象、无结论、需要方法论支撑"的场合

**什么时候不用**：已经有数据和分析结论 → 直接分析数据；纯粹要文档排版 → 用 ppt-builder。

## 工作流程（四步）

### 第 1 步：问清问题边界（不要跳过）

用户在描述问题时通常会漏掉关键信息。先确认这 6 件事（缺失的才问，一次问 3~5 个）：

1. **现象是什么**：具体表现为？在哪观察到？
2. **范围和对象**：涉及什么产品/设备/流程/人群？多少例？
3. **时间特征**：什么时候开始？持续多久？周期性还是突发？
4. **已排除什么**：已经查过哪些？结论是什么？（避免重复劳动）
5. **可用的证据**：有数据吗？有照片/日志/记录吗？能拿到什么？
6. **影响和紧迫度**：损失多大？什么时候必须有结论？

> 用户说"不清楚/你看着办"的，就按最保守假设推进，并在产出里标注假设。

### 第 2 步：选分析方法（关键步骤，不要堆砌所有方法）

按问题类型选**主方法 + 辅助方法**，最多 3 个，多了就是噪音。

| 问题类型 | 主方法 | 辅助方法 | 为什么 |
|---------|--------|---------|--------|
| 偶发/突发故障，原因不明 | 5Why + 鱼骨图 | 人机料法环 | 从现象追根因，先发散再收敛 |
| 同类问题反复出现 | 8D | 帕累托 + 5Why | 需要系统性闭环，不只是修一次 |
| 质量问题、批量失效 | 人机料法环（4M1E） | 鱼骨图 + 分层交叉 | 五个维度排查，警惕单维度假象 |
| 风险预防（还没出事） | FMEA | 鱼骨图 | 提前识别失效模式和风险优先级 |
| 问题很多、要先抓主要矛盾 | 帕累托 | 分层分析 | 80/20 定位关键少数 |
| 流程/管理类问题 | 5W2H + 5Why | 流程图分析 | 先界定问题，再找流程断点 |
| 数据异常/指标突变 | 分层分析 + 交叉分析 | 趋势分析、控制图 | 先拆维度看是不是某子集的问题 |
| 完全没头绪 | 5W2H（界定）+ 鱼骨图（发散） | — | 先把问题问清楚，再广泛列可能 |

**选择说明要写出来**：告诉用户"为什么选这几个方法"，而不是默默用。

### 第 3 步：用方法拆解问题空间

按选定方法展开，**每个分支都要落到"可观察、可验证"的程度**：

- 鱼骨图/人机料法环 → 每个维度的具体可能原因（不要写"设备问题"这种无法验证的）
- 5Why → 逐层追问链（可以给出多条候选链路，因为还没结论）
- FMEA → 失效模式 × 严重度/频度/可探测度 → 风险序数 RPN
- 帕累托 → 需要什么分类数据才能做（如果是"要做帕累托但没数据"，就写成数据采集任务）

### 第 4 步：产出可执行 checklist（本 skill 的核心交付物）

**格式要求**：每条必须能直接执行，包含五要素。

```markdown
| # | 排查项 | 怎么查（具体动作） | 判据：什么结果算排除/锁定 | 需要什么证据 | 负责人 | 状态 |
|---|--------|------------------|--------------------------|------------|--------|------|
| 1 | 批次 A 的物料是否为问题批次 | 调取 BOM + 来料检验记录，比对问题机台号段 | 若批次编号不在问题机段 → 排除 | 来料记录、机台日志 | 待定 | ☐ |
```

**五要素的意义**：
- **怎么查**：不能写"检查物料"，要写"调取 BOM 和来料检验记录，比对机台号段"
- **判据**：事先说清什么结果算排除、什么算锁定 —— 这是避免"查了但不知道算不算查到"的关键
- **证据**：明确要拿到什么书面/数据证据，方便归档
- **负责人**：留"待定"让用户填，不要瞎指派
- **状态**：勾选框，可打印使用

**排序原则**：按"排除效率"排序 —— 优先放**能一次性排除大范围**的检查项
（如"确认是否所有问题机都来自同一批次" 能一刀切掉一半假设），而不是按方法顺序。

## 输出结构（标准交付模板）

```markdown
## 问题界定
（用 5W2H 把问题说清楚：现象/范围/时间/影响/已排除）

## 分析方法选择
主方法：XXX（理由）
辅助方法：XXX（理由）

## 排查框架
（用选定方法展开的结构化拆解，可以是鱼骨图文字版/5Why 树/4M1E 矩阵）

## 排查清单（核心）
（表格形式，按排除效率排序）

## 建议的验证优先级
第一批查什么（最快缩小范围）、第二批查什么（确认根因）、第三批查什么（验证对策）

## 需要补充的信息
（如果要进一步分析还缺什么数据/证据）
```

## 方法速查

### 5W2H — 界定问题
What 什么现象 / Where 哪里发生 / When 何时 / Who 涉及谁或哪个批次 / Why 为什么是问题 /
How 多严重 / How much 量化（失效率、损失、频次）

### 人机料法环（4M1E）— 五维排查
人（操作者/班组/技能）、机（设备/工装/产线）、料（物料/批次/供应商）、
法（工艺/参数/流程）、环（温湿度/应力/环境）
**关键提醒**：警惕单维度假象 —— 某维度异常可能只是另一个维度分布不均造成的假关联，
必须做交叉验证（如料×环、料×机）。

### 鱼骨图（因果图）— 发散
按 4M1E 分类列出所有可能原因，每条都要能落到可验证的具体项。

### 5Why — 追根因
从现象连续追问"为什么"，直到找到**可行动**的根本原因。
不要停在"人员疏忽""环境不好"这类不可行动的层面。

### FMEA — 风险预防
失效模式 × 严重度(S) × 频度(O) × 可探测度(D) = RPN，按 RPN 排序优先处理。

### 帕累托 — 抓主要矛盾
按频次/损失排序，找累计 80% 的那几个类别。

### 8D — 系统闭环
D1 小组 → D2 描述问题 → D3 临时遏制 → D4 根因 → D5 永久对策 → D6 验证 → D7 预防 → D8 总结

### 分层/交叉分析 — 数据类问题
先按各维度拆开看（区域/时间/批次/产线），再两两交叉，定位问题集中的子集。

## 何时往下接 PPT

如果用户排查完要出汇报，把本 skill 的产出（问题界定 + 排查框架 + 排查结果）作为输入，
交给 `ppt-builder` 生成汇报 PPT（它内置了 8D / 鱼骨图 / Weibull 等呈现能力）。

**衔接要点**：本 skill 产出的"排查清单"可以直接变成 PPT 里的"排查矩阵页"；
"排查结果"里的排除项要保留展示，体现严谨性。

## 常见错误（避免）

- ✗ **一上来就堆 8 个方法**：用户会淹没。选 1 主 + 1~2 辅，说明理由。
- ✗ **checklist 写成"检查设备"**：不可执行。必须具体到"查什么记录/做什么测试"。
- ✗ **没有判据**：查完了不知道算不算查到，等于白查。每条都要有"什么结果算什么"。
- ✗ **直接给根因结论**：用户还没数据，你猜的根因是幻觉。给的是**假设和验证路径**。
- ✗ **忽略"已排除什么"**：重复排查用户已经做过的事，浪费且不专业。
- ✗ **按方法逻辑排序而非排除效率排序**：让人从最慢的查起。
